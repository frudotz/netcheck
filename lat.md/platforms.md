# Platforms

Support status per platform, stated at the evidence level actually reached; a target platform is not called supported until it is verified.

## Evidence levels

Every platform claim in this graph uses one of these levels, from strongest to weakest.

- **Verified** — run on the platform, with commands and results recorded in a merged PR or reproducible from the repository.
- **CI** — compiled (and, where noted, unit-tested) by [[.github/workflows/cross-platform.yml]] on every pull request; the app was not launched.
- **Simulator / emulator** — launched in a simulator or emulator with results recorded in a PR.
- **Reported** — stated by the developer from a session whose artifacts are not in the repository or on GitHub; treat as unconfirmed.
- **Unverified** — implemented or expected, but no run is recorded.

## Android

Android is the most thoroughly verified mobile target: emulator and one physical device, on both Wi-Fi and mobile data.

Verified (PR #23, PR #30) on the physical device:

- Real data and an ICMP socket ping to gateway, 1.1.1.1, and 8.8.8.8 concurrently (6/6 each).
- DNS, HTTPS, public IP, and all five diagnostics (score 100 on Wi-Fi).
- Mobile-data behavior, where the gateway is "Bulunamadı" and its test unavailable ([[networking#Network snapshot#Gateway selection]]).
- Live rotation, touch scrolling, the 4 information-page languages with RTL, and layouts at 392 px and 320 px.
- A locally debug-signed release APK.

Limitations: one device and one carrier. Release APKs are unsigned, and there is no keystore, AAB, or Play Store setup ([[tasks#Open work#NC-09 Android signed release]]). A brief "İnternet Yok" right after switching to mobile data was observed and deferred ([[tasks#Deferred#NC-06 Transient no-internet after network switch]]).

## iOS

The iOS project exists and runs in the simulator; physical-device results are reported but not reproducible from repository evidence.

- **Simulator (PR #28):** iPhone 17, iOS 26.5, `aarch64-sim` debug, built on macOS 26.6 / Xcode 26.6. The app launched, and the overview showed real local IP, gateway, DNS, public IP, and a Darwin-socket 1.1.1.1 latency. The simulator uses the host Mac's network and `/etc/resolv.conf`, so this is not device evidence. Tanılama, Rapor, Geçmiş, Ayarlar, languages, and RTL were not exercised there. PR #30 additionally checked the phone layout in the iPhone 17 simulator and the rail layout in the iPad Pro 13" simulator.
- **Project:** [[src-tauri/gen/apple]], generated by `tauri ios init` with no development team, local paths, or secrets committed. The entitlements file is empty and `ExportOptions.plist` uses the `debugging` method. Local signing settings belong on the developer's Mac and must stay uncommitted.
- **Physical iPhone:** PR #30 (Oct 11) recorded an iPhone 17 Pro on iOS 26.6.2 as BLOCKED because there was no signing identity. Later device smoke tests are reported, not recorded; see [[platforms#Historical claims]].
- **CI:** `cargo check --lib --target aarch64-apple-ios` and the macOS loopback ICMP test ([[tests#ICMP#Darwin concurrent loopback]]).

## Known limitations

Cross-platform limitations that are inherent to the design or not yet addressed.

- IPv6 ping targets are unsupported on all backends ([[networking#Ping backends]]).
- iOS DNS server discovery depends on `/etc/resolv.conf` ([[decisions#netdev features per target]]).
- The SQLite backend runs migrations at startup on mobile without any recorded runtime check ([[architecture#Local SQLite backend]]).
- Repository documents disagree on iOS status: [[README.md]], [[docs/proje-fikri.md]], [[docs/klasor-mimarisi.md]], and the Hakkında pages still call iOS planned or say it has no ping, while [[docs/mimari-agac.md]] records the simulator build ([[tasks#Open work#NC-10 Documentation consistency]]).
